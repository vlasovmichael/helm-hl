# Правило большого рефакторинга

Обязательно к исполнению для любого изменения, которое не влезает в один
коммит: разбиение файлов, перенос папок, смена API модулей, замена библиотеки.

## 0. Что считается большим

Изменение, которое **логически цельное, но физически не может быть одним
атомарным коммитом** — из-за объёма, конфликтов или числа затронутых файлов.
Это определение Google для LSC: мерило не «сколько строк», а «влезает ли в один
безопасный коммит».

Порог механизации — около **500 правок**. Выше него дешевле написать скрипт
(codemod), чем править руками: ручная правка на таком объёме гарантированно
даёт опечатки и невоспроизводима.

## 1. Что запрещено

- **Переписывание с нуля.** Новая система повторит старые баги и добавит свои
  (second-system effect). Старый код заменяется по частям, а не целиком.
- **Смешивать рефакторинг и поведение в одном коммите.** Коммит либо не меняет
  поведение вообще, либо меняет только его.
- **Шаг, который нельзя откатить одним `git revert`.** Если откат тянет за
  собой ещё три коммита — шаг слишком большой, дробить.
- **Рефакторинг кода без тестов.** Сначала сеть (пункт 2), потом касание.

## 2. Сеть безопасности — до первого касания

Для кода без тестов пишутся **характеризационные тесты**: они фиксируют
поведение как есть, не рассуждая, правильное ли оно. Задача — сделать
текущее поведение видимым до того, как оно начнёт меняться.

Правило проверки сети: **каждый характеризационный тест должен хотя бы раз
упасть**. Испортите значение намеренно, убедитесь, что тест покраснел, верните
обратно. Тест, который никогда не падал, не доказал ничего.

Для функций с широким выходом (сводки, отчёты, разметка) — golden master:
эталонный вывод записывается в файл и сравнивается посимвольно.

## 3. Техника замены

**Branch by abstraction** — внутри кода. Порядок строгий:

1. ввести абстракцию (модуль-фасад) поверх существующей реализации;
2. перевести всех потребителей на фасад — поведение не меняется;
3. написать новую реализацию за тем же фасадом;
4. переключить фасад на новую реализацию;
5. удалить старую.

Каждый из пяти шагов — отдельный коммит, который вливается и откатывается сам
по себе. Между шагами приложение работает.

**Strangler fig** — на границе системы: новый маршрут или страница обслуживают
часть трафика, старый код остаётся рядом, пока не останется без потребителей,
и только тогда удаляется.

## 4. Дробление

Каждый шаг обязан отвечать «да» на все четыре вопроса:

- вливается самостоятельно, не требуя следующего шага;
- откатывается одним revert;
- оставляет приложение рабочим;
- проходит `npm run verify` без обновления планок вверх.

Если хоть одно «нет» — шаг переразбивается.

## 5. Механизация

Свыше нескольких сотен однотипных правок — скрипт, а не руки. Скрипт кладётся
в `scripts/`, прогоняется, результат проверяется гейтом. Скрипт остаётся в
истории: он и есть документация того, что именно было сделано.

Ручные правки допустимы там, где требуется суждение: границы модулей, имена,
разбиение по смыслу.

## 6. Гейт и храповики

После каждого шага:

```bash
npm run verify
```

Планки (`comment-debt.json`, `size-debt.json`, `eslint-suppressions.json`)
двигаются только вниз. Сдвиг вверх означает, что шаг ухудшил состояние —
такой шаг не вливается.

## 7. Деплой

Выкатывать после каждого шага, а не в конце очереди. Десять выкаченных мелких
шагов диагностируются за минуты; один выкаченный большой — за вечер.

## 8. Чек-лист шага

- [ ] поведение не меняется (или меняется только оно — и тогда это не рефакторинг);
- [ ] тесты на затронутую логику существуют и хотя бы раз падали;
- [ ] шаг вливается и откатывается самостоятельно;
- [ ] `npm run verify` зелёный, планки не выросли;
- [ ] сообщение коммита говорит, что перенесено и откуда куда;
- [ ] выкачено и проверено на живом.

## 9. Очередь этого репозитория

От безопасного к рискованному. Целевая структура и правило зависимостей —
в `ARCHITECTURE.md`, там же таблица «куда что уезжает».

| Шаг | Файл                  | Сейчас | Цель                                                |
| --- | --------------------- | ------ | --------------------------------------------------- |
| 1   | `web/src/i18n.js`     | 1598   | `i18n/` — `index.js`, `en.js`, `ru.js`, `pl.js`     |
| 2   | `web/src/styles.scss` | 2654   | `styles/` — токены, база, компоненты, страницы      |
| 3   | `web/src/health.js`   | 1377   | `features/pressure/`, `features/journal/`, `pages/` |
| 4   | `web/src/main.js`     | 1083   | `app/router.js`, `app/state.js`, `app/masthead.js`  |
| 5   | `server/db.mjs`       | 594    | `infra/db/` по таблицам                             |
| 6   | `server/summary.mjs`  | 409    | `domain/summary/`                                   |

Шаг 1 механический: паритет ключей проверяет `npm run guard:i18n`, а вывод
словарей не меняется — сеть уже есть. Шаги 3 и 4 требуют характеризационных
тестов до начала: логика заперта в DOM-модулях и сейчас не тестируется.

## 10. Что нельзя менять по дороге

Рефакторинг переносит код. Всё перечисленное — контракт с внешним миром,
его трогают только отдельным изменением и с отдельным решением:

- адреса страниц (`/zdrowie`, `/cisnienie`, `/lekarz`) — ссылки разосланы;
- пути API (`/api/p/<кто>/…`) и форма ответов;
- схема базы и имена таблиц;
- пользовательские строки и ключи словарей;
- имена классов в SCSS — это контракт между разметкой и стилями;
- имена CSS-переменных: на них завязаны темы и другие проекты.

## 11. Ловушки конкретных шагов

**i18n.** Ключи объявлены тремя способами: `key:`, `get key()` (согласование
по роду) и функцией. Разбор, который видит только первый, объявит половину
словаря пропавшей. Паритет проверяет `npm run guard:i18n` — гонять после
каждого перемещения.

**SCSS.** Только `@use`, порядок важен: токены подключаются первыми, иначе
переменные не определены. Селекторы не переименовывать. После разбиения
сверить собранный CSS по размеру: расхождение больше пары процентов означает
потерянный или задвоенный блок.

**DOM-модули.** Сначала вынести чистую логику (расчёты, группировки, пороги)
в отдельный файл и покрыть тестами, и только потом двигать сборку разметки.
Обратный порядок оставляет логику непроверяемой.

**Сервер.** `domain` не импортирует express, `infra` не содержит правил.
Если при переносе понадобился обратный импорт — граница проведена неверно.

## 12. Кодемоды

Скрипт массовой правки: кладётся в `scripts/`, умеет прогон вхолостую,
идемпотентен (повторный запуск ничего не меняет), коммитится вместе
с результатом. Результат всегда проверяется гейтом, а не глазами.

## 13. Схема базы

Изменение схемы никогда не едет в одном коммите с переносом кода. Миграции
только вперёд, добавлением: новая колонка с умолчанием, обратная совместимость
чтения. Данные медицинские — потеря невосстановима, бэкап до миграции.

## 14. Мёртвый код

Удаление старой реализации — отдельный последний коммит шага, не часть
переключения. Так откат переключения не тянет за собой восстановление кода.

## 15. Что измерять на каждом шаге

Записывать до и после: размер бандла (`npm run build`), число файлов сверх
лимита (`guard:size`), долг комментариев, число тестов. Шаг, который увеличил
любую из первых трёх цифр, разбирается, а не вливается.

## 16. Стоп-правило

Гейт не зеленеет с третьей попытки или шаг разрастается за пределы задуманного
— откатить (`git revert`), вернуться к плану и переразбить. Не «дожимать»:
наполовину перенесённый модуль хуже непереносённого.

Рефакторинг и новые возможности не идут одновременно. Прилетел срочный фикс —
сначала он, потом продолжение шага от свежего `main`.
