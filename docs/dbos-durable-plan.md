# Durable execution для няньки: план, замеры и вердикт

Идея пришла из разбора 09.08: за шесть недель класс «зеркало ≠ биржа» чинился
восемь раз, плюс голодание пула, замерший тик и два тихих OOM. Общее у всех —
состояние сделки живёт в памяти процесса и в самописных сторах, а процесс
смертен. Durable execution (DBOS: библиотека + Postgres, без отдельного сервера)
обещал закрыть этот класс целиком.

План был из пяти шагов: (1) hello, durable workflow → (2) модель жизненного
цикла → (3) Postgres и деплой → (4) тень и сравнение → (5) переключение.

**Сделаны 1–3 и харнесс шага 4. Шаг 5 не начат, и по итогам замеров начинать
его в исходном виде не нужно — см. вердикт.**

## Шаг 1: пик переживает kill

`tools/dbosPgUp.mjs` (портативный Postgres из npm, в систему ничего не ставит),
`tools/dbosTrailLab.mjs` (миниатюра няньки). Прогон умирает на тике 4 с пиком
118, второй прогон доводит сделку с пиком 126 — максимум приходится на тик 5,
уже после смерти. Журнал побочных эффектов за оба прогона: десять строк, ни
одной повторной. Никакого файла состояния в лаборатории нет.

Читать надо именно журнал эффектов, а не консоль: тело воркфлоу при
восстановлении переигрывается целиком и печатает тики 0–4 второй раз, хотя их
тела не выполнялись.

Цена одного чекпоинта — **2.11 мс** (300 шагов за 632 мс).

## Шаг 2: модель настоящего жизненного цикла

`tools/dbosAdoptModel.mjs` — те же пороги, что у живой няньки, та же тройка
состояния (peak / trough / beArmed), те же два мягких выхода. Смерть на тике 300
с пиком +2.84% и взведённым BE; подъём, переход поколения на тике 500,
закрытие трейлом на тике 667 с пиком +3.75%.

Здесь же проверялись два моих собственных довода — оба не выжили.

**Довод «переигровка дорожает с возрастом позы» — опровергнут.** Замер честный:
процесс умирает на K-м шаге, второй процесс поднимает воркфлоу и доделывает
один оставшийся. Из времени вычтена базовая линия (старт ноды + launch DBOS,
1525 мс, медиана из трёх):

| шагов в истории | чистая переигровка |
|---|---|
| 100 | −25 мс |
| 1000 | −36 мс |
| 5000 | −25 мс |

Отрицательные числа — это шум процессного старта: переигровка 5000 шагов не
стоит ничего измеримого. (`forkWorkflow` для такого замера не годится — он
копирует строки в базе, тело не переигрывает. Первая версия замера мерила
именно это и показывала красивый линейный рост, которого нет.)

**Довод про рост таблицы — устоял, но лечится не поколениями.** Строка
чекпоинта — **482 байта** (17 538 строк = 8256 кБ). На 2-секундной петле это
~43 тысячи шагов и **~21 МБ в сутки на позицию**. Отсюда вывод для дизайна:
непрерывно меняющееся состояние надо писать не шагом на тик, а `setEvent` —
запись на месте, O(1) на позицию вместо O(тиков). Шаги остаются для того, у чего
есть побочный эффект: взвод стопа, перестановка, закрытие.

## Шаг 3: Postgres

Заготовка в `docker-compose.yml` — сервис `dbos-db` (postgres:16-alpine, лимит
256 МБ, свой том) **под профилем `dbos`**: обычный `docker compose up -d` его не
поднимает. Проверено `docker compose --profile dbos config` на сервере против
временной копии файла — прод не тронут, ничего не задеплоено.

Своя база, а не `tax-postgres`: там налоговый реестр, у потери разные
последствия и разные бэкапы. Место на Oracle есть (152 ГБ свободно), версии
Postgres везде 16.14.

## Шаг 4: тень — и вот тут план сломался

`tools/dbosShadowCompare.mjs`. Устройство замера важнее результата: **обе стороны
крутят один и тот же живой `analyzeAdopt`** из `src/modules/strategistAdopt.js`,
логика выхода не переписана и не пересказана. Различается только то, что
переживает рестарт:

- **store** — как в проде сегодня: `adoptTrailStore` пишет пик на диск, но лишь
  когда он дорос до `PERSIST_FROM_PCT` = min(BE_ARM, TRAIL_ARM) = 1.5%;
- **durable** — как было бы на DBOS: помнится каждый тик, без порога.

Рестарт эмулируется честно: `resetAdoptState()` гасит память процесса, модуль
поднимает состояние из своего источника.

Шесть сценариев, подобранных вокруг порога 1.5% (включая контрольный без
смертей):

```
расхождений в ВЫХОДАХ:  0
расхождений в MFE/MAE:  1   (пик 1.2% до смерти: store помнит 0.9%, durable 1.2%)
```

Это не случайность выборки, за этим стоит механика: **ниже 1.5% ни BE-храповик,
ни трейл не взводятся в принципе**, поэтому пик, который не дорос до порога, не
может повлиять ни на один выход. Пороговая запись в `adoptTrailStore` сохраняет
ровно то подмножество состояния, которое способно изменить решение. Тот, кто её
писал 09.08, угадал границу правильно.

Оговорка про силу утверждения: сценариев шесть и они синтетические. Несёт вывод
не их количество, а разбор кода; харнесс лишь подтверждает, что код прочитан
верно. Не покрыт и остаётся открытым узкий зазор: смерть между обновлением пика
в памяти и синхронной записью файла. DBOS его тоже не закрывает — у чекпоинта
такое же окно.

## Вердикт

Исходное обоснование переписывания — «durable уберёт самописные сторы состояния»
— **замером не подтвердилось**. На выходах няньки durable-состояние не меняет
ничего; выигрыш сводится к полному MFE/MAE для разбора, отсутствию порога, о
котором надо думать, и видимому статусу вместо файла с прополкой орфанов по TTL.
Это аргументы за аккуратность, а не за две недели работы над кодом, который
держит деньги.

Что при этом **не проверено и остаётся живым**: класс «зеркало ≠ биржа» — это не
про пик трейла, а про расхождение строки в БД с состоянием на бирже
(`adoptReconcile`, 598 строк, восемь фиксов за шесть недель). Там durable
execution даёт то, чего сторами не добьёшься: идемпотентность биржевого вызова
через client order id и гарантию, что «открыл ордер → записал в БД» не
разорвётся посередине. Шаг «хотя бы один раз» без client order id, наоборот,
даёт двойное закрытие — так что это обязательное условие, а не украшение.

**Предложение:** пятый шаг в исходном виде (переключить нянькин трейл на DBOS)
снять. Если возвращаться к теме — начинать с `adoptReconcile` и мерить по числу
расхождений зеркала, а не по выживанию пика. И не раньше сентябрьских ворот.

## Как запустить лабораторию

Зависимости намеренно не в `package.json`: эксперимент может не дожить до
внедрения, а дерево зависимостей боевого бота дороже удобства.

```
npm i --no-save @dbos-inc/dbos-sdk embedded-postgres
node tools/dbosPgUp.mjs                            # терминал 1, Ctrl+C чтобы погасить
node tools/dbosTrailLab.mjs reset && node tools/dbosTrailLab.mjs run --crash-at 4
node tools/dbosAdoptModel.mjs run --crash-at 300
node tools/dbosAdoptModel.mjs replay-cost
node tools/dbosShadowCompare.mjs
```
